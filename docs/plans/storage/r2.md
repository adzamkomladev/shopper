# Native R2 storage and staging portal

The owner authorized native R2 internal operations, bucket/key provisioning, Worker and local secrets, and staging portal deployment.

## Scope and checks

- Keep snapshot buckets and legacy colon-normalized keys; bind imports separately with raw tenant-prefixed slash keys.
- Use S3 only to sign cloud browser upload grants. The box retains RustFS S3 transport.
- Test native puts/reads/deletes with an unreachable S3 endpoint, bounded reads, tenant isolation and missing signing credentials. Verify S3 grants separately against RustFS.
- Serve the existing portal SPA with a native API service binding, retaining `/api/auth`, request bodies, query strings, cookies and Origin. Keep API errors out of SPA fallback.
- Deploy the Vite plugin's generated staging config with `wrangler deploy` (Workers Builds; see `docs/engineering/deployment.md`). The generated names already select staging.

## Provisioned storage

Account and resource identifiers remain in the owning Worker configuration. Existing private snapshot buckets are `shopper-assets-dev` and `shopper-assets-staging`; newly provisioned private import buckets are `shopper-imports-dev` and `shopper-imports-staging`.

Each imports bucket has its own Object Read & Write signing token scoped to that bucket. Staging credentials are installed as Worker secrets; dev credentials configure local workerd. All local credentials are saved only to ignored files with mode 0600. Root `.env` and `apps/edge/.dev.vars` hold dev credentials; `.env.staging` and `apps/edge/.dev.vars.staging` hold staging credentials. The latter does not contain the database migration connection.

Dev PUT CORS permits exact loopback portal origins on port 5173. Staging permits `https://shopper-staging.temtem.dev`. Public r2.dev access remains disabled.

A live provider check uploaded through the actual adapter's signed URL, read and wrote through native remote R2 bindings, enforced read bounds and tenant isolation, rejected anonymous reads, and rejected signing credentials on the other imports bucket and snapshot bucket. Both environments passed. All verification objects were removed.

## Staging prerequisites

The existing staging Hyperdrive endpoint was matched to Neon's staging branch before any mutation. Its empty application schema received the existing forward-only migrations, and staging D1 received the cache migration. Production was not changed. Dedicated authentication/link secrets and the portal auth origin are configured for staging; existing Maileroo secrets are preserved.

Deployment and browser verification results are recorded after publishing.
